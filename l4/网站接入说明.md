# L4 情绪与衍生品层 · 网站接入说明（交给 Claude Code 照做）

和 L2、L3 是同一套做法：一个 Python 脚本每天跑一次，输出两个 JSON；前端只读 JSON 展示，不做任何计算。页面展示什么、文案怎么写，见项目文档《L4网页数据维度规格》。

## 1. 这个文件夹是什么

| 文件 | 作用 |
|---|---|
| `l4_daily.py` | 每天跑一次：取资金费率、季度合约升水、CME 升水、全市场 OI 与清算、恐慌贪婪、DVOL、CFTC，算一条信号、八个温度读数、六个观察项，输出 JSON |
| `l4_seed.csv` | 研究用的历史数据（2023-09 起），给“过去 730 天分位”打底；之后每天自动追加到缓存 |
| `requirements.txt` | 依赖：pandas、numpy、requests |
| `.github/workflows/l4-daily.yml` | GitHub Actions 定时任务：每天 UTC 03:17（北京时间 11:17），排在 L2、L3 之后（要读当天的 L2 状态），结果提交回仓库 |
| `output/`（运行后生成） | `l4_latest.json`（今日结论）、`l4_history.json`（近 400 天） |
| `cache/`（运行后生成） | 累积的日度面板 `l4_panel.csv`、资金费率换源校准记录 `funding_calib.json` |

## 2. 接入步骤

1. 把本文件夹放进网站仓库的 `l4/` 目录（和 `l2/`、`l3/` 并列）。
2. 把 `.github/workflows/l4-daily.yml` 放到仓库根目录的 `.github/workflows/`。workflow 已按仓库现行写法配好（输出 `data/l4/`、缓存 `l4/cache` 走 actions/cache、和日更 / L2 / L3 共用 `daily-pipeline` 并发组、跑完重出网站并提交 `data/l4` 与 `site/`）。
3. **Coinalyze 免费 key**：站长在 coinalyze.net 注册后在 API 页面复制 key，放到仓库 Settings → Secrets and variables → Actions → New repository secret，名字 `COINALYZE_KEY`。没有 key 时：资金费率自动改用 BitMEX / OKX / Deribit，全市场 OI 和清算两项显示“数据延迟”，其余照常。
4. 在 Actions 页面手动点一次 “Run workflow”，确认生成了 `l4_latest.json`，`data_status.detail.funding` 是 `ok（…）`。
5. 前端只读 `l4_latest.json` 和 `l4_history.json`。**替换掉现在的 L4 温度计**（未平仓合约 7 日变化 > 资金费率 > 恐慌贪婪那一套），它没有经过检验。

## 3. 数据源（都能在 GitHub 的美国机房访问）

Binance、Bybit 的接口在美国机房返回 451 / 403，所以不用。

| 读数 | 来源 | 说明 |
|---|---|---|
| 资金费率 | Coinalyze 的 Binance BTCUSDT 永续 → BitMEX → OKX → Deribit，按顺序第一个取到的为准 | 研究用的是 Binance（2020 起）+ BitMEX（之前）。换源时脚本用和历史重叠的日子自动算比例，相关低于 0.5 的源不用；比例记在 `cache/funding_calib.json` |
| 季度合约年化升水 | Deribit，剩余 28~120 天最近的一张 | 研究用 Binance 币本位季度合约；10-13 起换源，分位仍在研究数据上算，前几个月有轻微口径差 |
| CME 升水 | Yahoo BTC=F ÷ Coinbase 20:00 UTC 现货，5 日均 | 和研究一致 |
| 全市场 OI、清算 | Coinalyze，固定一篮子主流合约（OI 12 个、清算 9 个） | 和研究一致；篮子不齐的日子不算 |
| 恐慌贪婪 / DVOL / CFTC / 价格与交易所余额 | alternative.me / Deribit / CFTC / Coin Metrics | 和研究一致 |

## 4. `l4_latest.json` 字段

| 字段 | 内容 | 展示建议 |
|---|---|---|
| `data_date` / `updated_utc` | 数据日期 / 运行时间 | 卡片角标 |
| `conclusion.level` | `信号` / `过热` / `偏热` / `中性` / `偏冷` | 结论区大号状态 |
| `conclusion.one_liner_zh` | 综合研判里用的短句（中性时为空，不进一句话） | 综合研判 L4 段；见规格 §5 |
| `conclusion.paragraph_zh` | 结论区一段话 | 直接显示，不改写 |
| `conclusion.leverage_band_zh` / `sentiment_band_zh` / `composite_pct` / `key_reading_zh` | 杠杆档、情绪档、综合分位、关键读数 | 结论区副标题 |
| `signal` | 唯一改动作的规则：`on`、`value_pct`（30 日均年化 %）、`days_on`、`since`、`l2_state`、`funding_source`、`use_zh`（今天的用法）、`grade`、`stat_zh`、`rule_zh` | 主卡：一个灯 + 当前值 + 0 线；亮时显示“已连续 N 天”和 `use_zh` |
| `thermometer[]` | 八个温度读数：`name_zh`、`value`、`unit`、`pct_730d`（过去两年分位）、`band_zh`、`grade`（都是“描述”）、`stat_zh`（为什么只是描述） | 一排小卡：读数 + 分位条 + 档位色；卡底小字写 `stat_zh` |
| `watch[]` | 六个观察项：`on`、`name_zh`、`grade`（都是“假设”）、`stat_zh` | 折叠列表，亮的排前面，标“假设 · 不改动作” |
| `summary_zh` | 已写好的每日结论全文（多行） | 解读日志直接用 |
| `data_status.stale` / `detail` / `notes` | 有数据源没取到时为 true，写明哪个源 | true 时对应卡片显示灰色“数据延迟” |

`l4_history.json`：每天一条，含 `price`、`fund_ma30`、`fund_ma7`、`signal`、`qbasis`、`cme_prem`、`agg_oi_chg7`、`agg_oi_mcap`、`liq_total_oi`、`fng`、`dvol` 和几项分位。主图建议：价格 + 资金费率 30 日均（0 线标出，为负的区间染色）。

## 5. 页面上必须有的说明（模块下方小字）

> 只有“资金费率 30 日均转负”一条通过了历史检验，会改变动作；其余读数只描述温度。费率高要回调、恐慌是买点、OI 堆积会瀑布、低波动是大行情前夜，这些常见说法用我们的口径检验都不成立。分位 = 今天的值在过去两年里排第几。样本有限，最高到“已验证·方向”，不构成投资建议。

## 6. 运行失败怎么办

- 某个数据源当天取不到：用缓存继续算，`data_status.stale = true`，网站照常显示。资金费率底层数据超过 5 天没更新时，信号显示“数据延迟，今天不判断”，不会拿旧值顶替。
- 所有资金费率源都和历史对不上：`notes` 里会写原因，信号停判；这时需要回到研究里重新核对口径。
- 本地试跑：`python l4_daily.py`，输出在 `output/`。离线测试：`L4_OFFLINE=1 L4_TODAY=2026-04-10 python l4_daily.py`（用种子数据，2026-04-10 那天信号是亮的）。

## 7. 不要做的事

- 不要把温度读数做成红绿“看多 / 看空”信号，也不要写“过热 → 小心回调”这类话。
- 观察项不要和信号放在同一视觉层级；它们是假设。
- 不要改脚本顶部的参数（730 天、365 个观测、30 日均、0 阈值、分档边界）；要改先改研究文档。
